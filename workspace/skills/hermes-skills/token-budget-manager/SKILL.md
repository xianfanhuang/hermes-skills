# Token Budget Manager v2.0

> 🛡️ 主动防线——不是等你发现烧钱了才补救，而是在烧钱之前拦截
> 
> v2.0核心升级：从"计轮次"升级为"计真实成本"，output单价是input的2.5倍

## 核心理念

**v1.0的盲区**：只看轮次和工具调用数，忽略了output膨胀。
**v2.0的核心**：轻量优先——无论是否有积分成本，系统的每个环节都应尽可能轻。

### 轻量设计哲学（2026-05-23 新增）

**为什么轻量**：
- 不只是为了省积分
- 信息密度 > 信息总量
- 快速迭代 > 完美交付
- 用户的注意力是最稀缺的资源

**轻量的三个维度**：
1. **回复轻量**：≤3句话能说清的事，不要写一段
2. **流程轻量**：能1步完成的，不要拆成3步
3. **架构轻量**：能不spawn的，不要spawn

**成本现实**（顺便的事）：
- output单价是input的2.5倍
- 冗长回复 = 浪费用户时间 × 浪费计算资源

**问题根因**：
1. 主对话上下文越长 → input线性增长
2. **Agent回复过长是最大浪费**（output单价2.5x + 用户阅读时间）
3. 工具返回结果（search结果、文件内容）也是input大户
4. 群聊消息噪音触发不必要的LLM调用

**设计原则**：
1. **轻量 > 完整**：优先交付核心结论，细节可追问
2. **真实成本 > 代理指标**：output长度×2.5 + 工具结果长度 > 简单的轮次计数
3. **主动 > 被动**：不等用户发现问题才补救
4. **可测量 > 凭感觉**：用轮次/输出长度/工具结果大小作为代理指标
5. **跨域复用**：主对话、子session、cron任务、群聊session都能用同一套规则

## 三层防线架构

### L1: 会话内自检（每轮自动执行）

**触发条件**：Agent每次回复前自动检查（零成本，纯规则判断）

| 指标 | 黄色预警 | 红色熔断 |
|------|---------|---------|
| 对话轮次 | >30轮 | >50轮 |
| **单轮output长度** | **>1K字** | **>2K字** |
| 单轮工具调用 | >8次 | >15次 |
| 连续搜索轮数 | >3轮 | >5轮 |
| 工具返回结果总长 | >5K字/轮 | >10K字/轮 |

**黄色动作**：
- 回复末尾追加 `⚠️ [token-notify] 当前对话已{N}轮，建议近期归档`
- 搜索/分析任务强制派子session
- **主动裁剪工具返回结果**：search_web用response_length=short/medium

**红色动作**：
- 立即执行摘要归档流程，回复"已归档完毕，请 /new"
- 之后**拒绝响应本对话的所有请求**（定时任务/子session不受影响）
- 禁止继续在主对话做重活

**v2.0新增：Output成本意识**
- 回复前自检：如果预估输出>1K字，先问自己"能不能5行说清楚？"
- 工具结果裁剪：read_file用limit参数，search_web用short/medium
- 禁止在主对话做"长文生成"——交给子session

### 轻量回复规范（2026-05-23 新增）

**核心原则**：信息密度 > 信息总量

| 场景 | 轻量标准 | 反例 |
|------|---------|------|
| 确认收到 | "收到"/"👌"/"了解" | "我已经收到了您的请求，接下来我将..." |
| 状态汇报 | 3句话以内 + 关键数据 | 大段文字描述每个细节 |
| 方案选择 | A/B/C 各一行 | 每个选项写一段分析 |
| 任务完成 | "已完成：[结果]" | 复述整个过程 |

**禁止行为**：
- ❌ 用表格展示简单信息（如上面这个表格，实际应该用纯文本）
- ❌ 每句话后面跟emoji装饰
- ❌ 重复确认已知信息（"如我之前所说..."）
- ❌ "让我为您总结一下..."（直接给结论）

**允许行为**：
- ✅ 一句话回复
- ✅ 直接给结论，细节追问时再展开
- ✅ 用列表代替段落（信息密度更高）
- ✅ 用户明确要详细时，再详细

### L2: 定时巡检（Calendar任务）

**任务**：token-budget-patrol，每日2次（15:00+21:00）

**检查项**：
1. 读取 `budget_state.json` 获取当前状态
2. `sessions_status` 检查主对话session运行时长
3. `sessions_list` 统计running子session数量和时长
4. 检查 `./对话摘要/` 最近归档时间
5. 估算当日积分消耗（v2.0加权公式）
6. **检查飞书/群聊session活跃度**（跨渠道消耗）

**v2.0加权估算公式**：
```
估算消耗 = Σ(各session)
  单session消耗 ≈ output字数×2.5 + (工具结果字数 + 上下文字数)×1.0
  主对话上下文 ≈ 轮次 × 2KB
```

**产出**：
- 更新 `budget_state.json`
- 超阈值通知主人
- 正常则NO_REPLY

### L3: 跨域规则注入（SOUL.md/TOOLS.md）

所有Agent session共享的核心规则，写入 `基础设定/TOOLS.md`：

```
## Token预算铁律（v2.0 跨域通用，基于轻量优先）
1. **轻量第一**：≤3句话能说清的事，不要写一段
2. 主对话>50轮 → 自动归档，拒绝后续请求（定时任务/子session不受影响）
3. **output单价=2.5×input** → 回复≤5行是最高效的省钱方式
4. 工具结果裁剪：search用short/medium，read_file用limit，禁止拉全量
5. 日工具调用>50 → 黄色，>100 → 红色
6. **spawn策略**：能自己完成的短链路，不要spawn
7. cron任务prompt注入≤2K字
8. 子session单次任务≤30分钟，注入Token规则
9. **群聊/飞书session**：只响应@消息和关键词触发，忽略闲聊
```

## 子session轻量策略（2026-05-23 新增）

**Spawn不是解药，是开销**。每次spawn：
- 传递完整上下文（几千token）
- 子session内同样消耗积分
- 结果返回后还要在主对话处理

**轻量决策树**：
```
任务来了？
├─ 能1-2步完成？→ 自己做
├─ 需要浏览器/搜索？→ 先自己查，结果轻量汇报
├─ 明确独立闭环+长耗时？→ 再spawn
└─ 能批处理/异步？→ Calendar定时任务更好
```

**Spawn时的轻量原则**：
1. task描述≤500字，不要复制整段文档
2. 只传必要上下文，不传完整对话历史
3. 明确交付物，避免无限迭代
4. 设置run_timeout，不要无限等待

- 前缀缓存在我们的工具调用场景完全不可用
- **聚焦L1-L3可落地方案**：Output长度控制、工具结果裁剪、群聊过滤

## 摘要归档流程（L1红色触发时执行）

1. 生成当前对话摘要（目标、进度、关键决策、未完成项、关键文件路径）
2. 保存到 `./对话摘要/YYYY-MM-DD_摘要.md`
3. 更新 `MEMORY.md` 中的进行中任务状态
4. 更新 `budget_state.json`（归档计数+1，重置轮次）
5. 回复主人："对话已归档，建议 /new 开新对话"

## 使用方式

### 主对话使用
- Agent自动遵循L1规则，无需显式加载
- L2巡检由Calendar任务自动执行

### 子session使用
- **轻量优先**：能自己完成的短链路，不要spawn
- 必须spawn时，在task描述中注入轻量规则（≤500字）：
  ```
  Token规则：工具调用>15次或运行>25分钟时，优先交付当前成果并返回，不要无限迭代。输出≤2K字。
  ```
- 不要复制整段文档，只传必要上下文

### Cron任务使用
- description中已包含"严禁在扣子对话中做批量内容处理"等规则
- prompt注入控制在2K字以内

## 关键指标估算公式

| 指标 | 估算方法（v2.0加权） |
|------|---------|
| 单轮真实成本 | output字数×0.5×2.5 + (工具结果字数+上下文字数)×0.3 |
| 日消耗估算 | Σ各session真实成本 |
| 上下文膨胀率 | 对话轮次 × 2KB（含工具调用历史） |
| 归档ROI | 归档后首轮消耗 / 归档前末轮消耗（应<0.1） |

## 跨渠道消耗追踪

| 渠道 | 消耗特征 | 监控方式 |
|------|---------|---------|
| 扣子主对话 | 轮次×上下文膨胀为主 | L1自检+L2巡检 |
| 扣子子session | task描述+独立运行 | sessions_list时长检查 |
| 飞书DM | 独立session，共享积分 | sessions_list飞书渠道 |
| 飞书群聊 | **高风险**：每条群消息触发LLM | 群消息频率监控 |
| Cron任务 | 固定prompt注入成本 | Calendar执行频率 |
