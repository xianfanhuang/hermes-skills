# Coze Token消耗机制深度分析
> 2026-05-21 底摸清报告

## 一、计费模型：Output才是真正的成本黑洞

### 资源点计费（豆包模型，扣子专业版）

| 模型 | 输入(点/千tokens) | 输出(点/千tokens) | 输出/输入倍率 |
|------|------------------|------------------|-------------|
| Doubao-pro-32k | 0.8 | 2.0 | **2.5x** |
| Doubao-1.5-pro-256k | 5.0 | 9.0 | **1.8x** |
| Doubao-lite-32k | 0.3 | 0.6 | **2.0x** |
| Doubao-1.5-vision-pro | 3.0 | 9.0 | **3.0x** |

### Coze Token计费（API/SDK调用）

| 模型 | 输入(1M tokens) | 输出(1M tokens) | 输出/输入倍率 |
|------|----------------|----------------|-------------|
| GPT-4o 8K | $5.00 | $15.00 | **3.0x** |
| GPT-4 Turbo 128K | $10.00 | $30.00 | **3.0x** |

### 对我们的影响

**我们的典型一轮对话token分布**：
- 用户input: ~50-200 tokens（用户说的话很短）
- 系统prompt+上下文: ~5000-50000 tokens（随轮次膨胀）
- 工具调用请求: ~500-2000 tokens/次
- 工具返回结果: ~1000-10000 tokens/次（搜索结果、文件内容等）
- Agent回复(output): ~500-3000 tokens

**单轮积分消耗估算**（以Doubao-pro为例）：
- 输入端: (系统prompt + 历史 + 工具结果) × 0.8/千
- 输出端: (Agent回复 + 工具调用请求) × 2.0/千
- **输出虽然token数少，但单价2.5倍，实际占比40-60%**

**关键结论：控制output长度比控制input更有效。**

## 二、前缀缓存机制：我们的场景基本用不上

### 工作原理
- 将重复的、固定的提示词片段缓存，后续只传动态部分
- 当前命中缓存的tokens限时免费

### 两个API模式的差异

| 特性 | Context API | Responses API |
|------|------------|---------------|
| 前缀缓存 | ✅ 支持 | ✅ 支持 |
| 工具调用(Function Call) | ❌ 互斥 | ✅ 同时支持 |
| 变量/插件 | ❌ 互斥 | ✅ 支持 |
| 获取当前时间 | ❌ 互斥 | ✅ 支持 |

### 我们的场景分析
- 我们**重度依赖工具调用**（bash、search、文件操作等）
- Context API下开启前缀缓存 → 工具调用被禁 → 完全不可用
- **出路：切换到Responses API**，但需确认当前模型是否支持

### 缓存命中率影响因素
- 包含动态变量（获取当前时间）→ 不命中
- 工具调用改变上下文结构 → 打破前缀 → 不命中
- 缓存TTL最长3天，访问不续期

## 三、群聊与多渠道token消耗机制

### 群聊场景
- 群内**每条消息**都可能触发Agent一次完整LLM调用
- 所有群成员的消息成为上下文的一部分
- 上下文膨胀速度 = 群消息频率 × 平均消息长度
- **一条无关消息也可能触发Agent思考并消耗tokens**

### 飞书渠道
- 飞书session与扣子session**独立**，但**共享积分池**
- 飞书端每次交互 = 一次完整LLM调用
- sessions_send跨session通信 = 额外的LLM调用（接收端session也要处理）
- **风险**：飞书群聊中其他人的消息也会触发Agent

### 子session (sessions_spawn)
- 每个子session有独立上下文，不继承主对话历史
- 但task描述会作为首次输入（需控制在2K字以内）
- 子session的工具调用同样计费
- **子session的总消耗 = prompt输入 + N轮工具调用 + 最终输出**

### Cron/Calendar任务
- 每次触发 = 独立session + 完整prompt注入
- prompt注入长度直接影响单次成本
- 有缓存命中（相同prompt前缀），但不稳定

## 四、我们场景的消耗模型

### 消耗源分类与占比估算

| 消耗源 | 占比估算 | 特征 | 可控性 |
|--------|---------|------|-------|
| Agent回复(output) | 30-40% | 单价2.5x，长度可控 | ⭐⭐⭐ 高 |
| 工具调用结果(input) | 25-35% | 搜索结果/文件内容往往很长 | ⭐⭐ 中 |
| 上下文历史(input) | 15-25% | 随轮次线性增长 | ⭐⭐ 中 |
| 系统prompt(input) | 5-10% | 固定开销，缓存可覆盖 | ⭐ 低 |
| 工具调用请求(output) | 5-10% | Function Call的参数 | ⭐ 低 |
| 子session调度 | 10-20% | 上下文传递+独立运行 | ⭐⭐ 中 |

### 五大烧钱场景

1. **长上下文连续对话**：历史消息每轮重复计费，50轮后单轮input可达50K+ tokens
2. **工具返回结果过长**：search_web返回大量文本、read_file读取大文件 → 全部进入input
3. **群聊消息噪音**：群内无关消息触发Agent思考和回复
4. **子session上下文传递**：spawn时传递完整上下文，子session又独立消耗
5. **cron任务prompt过长**：description过长直接增加每次触发的固定成本

## 五、预算系统迭代方向

### 当前v1.0的盲区
1. ❌ 只监控"轮次"和"工具调用数"，没监控output长度
2. ❌ 没考虑output/input 2.5倍价差
3. ❌ 没考虑群聊/飞书渠道的独立消耗
4. ❌ ~~Responses API切换~~：**已确认不可用**——Coze内置模型无协议类型选项，前缀缓存在我们场景基本用不上
5. ❌ 工具返回结果的长度完全没控制

### v2.0迭代要点
1. ✅ **Output长度硬限**：主对话回复≤5行、子session输出≤2K字
2. ✅ **工具结果裁剪**：search_web用response_length=short/medium，read_file用limit参数
3. ✅ **群聊消息过滤**：飞书群只响应@消息和关键词触发，忽略闲聊
4. ~~✅ Responses API切换~~：**确认不可行**，聚焦其他4项可落地方案
5. ✅ **按价差加权计分**：不是简单计工具调用次数，而是 output_tokens×2.5 + input_tokens×1
